# LEARN-0005 · 캘린더 계약에서 날짜·관계·버전을 나누는 이유

- 종류: 예방 설계/학습 초안. 실제 운영 장애·성능 개선 사례가 아니다.
- 근거 원본: [backend 계약](https://github.com/joobang/godieor-backend/tree/main/contracts), backend ADR-008. 정확한 고정 버전은 이 저장소 docs/contracts/reference.json.
- 관련 요구: PROD-001/003/005~008. 독립 검증/사용자 설명 완료 상태는 아니다.

## 왜 이 구조인가

작품 한 개에도 시즌/지역/기기별 공개 이벤트가 여러 개라 작품과 달력 행을 분리한다.
날짜만 있는 개봉일을 UTC 자정으로 저장하면 표시 시간대가 바뀔 때 날짜가 달라질 수 있어 별도 date로 보존한다.
카탈로그 조회 중 수집이 바뀌면 월 합계와 목록 페이지가 어긋날 수 있다. revision을 묶고 변경 시 재조회하는 초안을 택했다.

## 대안과 한계

단일 timestamp/단일 다형 찜 테이블/모든 과거 snapshot 보관은 각각 단순함 또는 연속 조회에 장점이 있다.
현재는 날짜 왜곡 방지, 명시적 FK, 작은 규모의 단순 재조회가 우선이다. 잦은 변경/대규모 이력이 생기면 다시 검토한다.
SQL CHECK는 NULL 결과도 허용하므로 필수 값은 NOT NULL 또는 명시적 IS NOT NULL로 다룬다.
단일 행 제약은 다른 테이블에 service가 최소 한 개 있는지를 대신 보장하지 않는다. 도메인 publish 트랜잭션과 독립 DB 확인이 별도 필요하다.

## 이번 근거와 미실행

계약 초안·가상 응답·문서/참조 구조를 작성했다. 서버/Prisma migration/실제 DB 실행은 없다.
PostgreSQL 공식 제약 문서와 OpenAPI/Google 공식 근거는 backend/contracts/README.md에 연결했다.
YAML 파싱·참조/파일 해시 확인은 형식 점검이며 제품 동작 통과 증거가 아니다.

## 스스로 설명해볼 질문

- 날짜만 있는 자료를 Date로 바로 변환하면 어떤 조건에서 하루가 어긋나는가?
- DB가 FK를 검사해도 최소 한 서비스 연결을 자동 보장하지 않는 이유는?
- calendarRevision만 고정하고 개인 찜 버전을 고정하지 않으면 어떤 문제가 생기는가?

## 후속 상태

이 글은 계약 작성 시점의 설명이다. 이후 로컬 DB/파이프라인 구현·구동 기록은 [LEARN-0006](0006-local-pipeline.md)에 연결했다. 독립 실행 검증은 계속 미완료다.
