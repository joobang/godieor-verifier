# LEARN-0015 · Docker가 꺼져 있는데 iOS 빌드까지 건너뛴 이유

이 글은 로컬 검사 실행기를 고치면서 드러난 **검사 간 의존성 설계**를 설명한다. Docker는 이 프로젝트에서 검사에 쓸 임시 PostgreSQL을 실행하는 데 사용한다. iOS 앱을 컴파일하는 Xcode 빌드에는 그 DB가 필요하지 않다. 그런데 당시 실행 순서에서는 Docker 준비가 실패하면 iOS 빌드도 실행되지 않았다.

이 사례에서 배울 것은 작업을 한 줄로 나열하는 것과, 실제 의존 관계에 맞게 연결하는 것의 차이다.

## 실행 순서가 불필요한 의존성을 만들었다

다음은 당시 문제를 단순화한 **설명용 의사코드**다.

```text
DB 준비 → backend 검사 → iOS 빌드
어느 단계든 실패하면 즉시 전체 종료
```

이렇게 연결하면 “DB가 준비되어야 backend의 DB 검사를 할 수 있다”는 필요한 조건과 “DB가 준비되어야 iOS를 컴파일할 수 있다”는 불필요한 조건이 함께 생긴다. Docker가 꺼진 한 가지 환경 문제 때문에, 앱 컴파일 오류가 있는지조차 알 수 없게 된다.

그 결과 “iOS 검사 실패”와 “iOS 검사를 실행하지 못함”도 구분해야 한다. 전자는 빌드 명령의 결과이고, 후자는 실행기 흐름의 결과다. 해결해야 할 곳이 다르다.

## 선택한 구조: 독립된 검사는 실패해도 각각 결과를 남긴다

수정은 iOS 빌드를 먼저 독립 실행하고, 그 성공 여부와 별개로 backend 검사에 진입하도록 했다. DB 준비가 실패하면 DB에 의존하는 검사는 실행할 수 없지만, 이미 얻은 iOS 결과는 남는다.

```text
고정 소스 준비
  ├─ iOS 빌드 → 빌드 결과 저장
  └─ backend 준비 → 임시 DB 준비 → DB/API 검사
각 단계의 결과 수집 → 전체 결과 집계
```

그림의 가지는 **의존 관계**다. 두 작업을 실제로 동시에 실행한다는 뜻은 아니다. 당시 구현은 순차 실행을 유지하면서 한 가지 실패가 관계없는 가지를 막지 않게 바꿨다.

다음 표는 원본에 기록된 선택을 이해하기 위한 사후 대안 비교다. 모든 대안을 당시 실제 실험했다는 뜻은 아니다.

| 대안 | 얻는 것 | 이 사례의 비용·문제 |
|---|---|---|
| 첫 오류에서 전부 중단 | 실행기 구현이 단순하고 남은 비용을 아낌 | 관계없는 검사 결과도 잃음 |
| 실패해도 모든 명령을 무조건 실행 | 많은 결과를 모음 | DB 없는 상태에서 DB 검사를 실행해 원인과 후속 오류가 섞임 |
| 의존하는 단계만 건너뛰고 독립 검사는 계속 | 어느 부분이 잘못됐는지 구체적으로 남김 | 실행 여부·실패·누락을 별도로 관리해야 함 |

세 번째 방식을 택한 이유는 실패를 무시하려는 것이 아니라, 한 번의 실행에서 얻을 수 있는 유효한 관찰을 보존하기 위해서다. 마지막 집계에서는 실패와 필수 검사 누락이 그대로 남아야 한다.

## 실제로 확인한 범위

2026-11-10 작업 기록에는 Docker 서비스 미기동과 npm 연결 중단이 각각 남아 있다. 이후 고정된 소스의 서명 없는 iOS 빌드와 backend 검사·임시 DB 검사를 실행했다. iOS 실패 뒤 backend를 계속하는 경우 등은 모의 실행으로 확인했다. 실제 환경 실패와 모의 검사는 [원본 카드](../../tasks/VFY-local-verification.md)에 구분되어 있다. 여기 적힌 결과는 당시 기록이며 이번 편집에서 재실행한 결과가 아니다.

같은 작업에서 전용 macOS 계정을 필수 조건으로 삼던 방식도 사용자가 폐기했다. 이것은 **실행 권한 정책**에 관한 별도 결정이다. 기존 계정에서 컴파일이 됐다는 결과는 앱 컴파일 가능성의 근거다. 실행 코드가 개인 파일에 접근하지 못한다는 보장은 별도의 권한 경계 검사에서 얻어야 한다. 현재 정책은 [로컬 검증 정책](../../local-verification.md)이 소유한다.

## 이 글에 붙어 있던 DATA-48 기록은 왜 분리하는가

후속 작업에서 실행기가 `*.test.cjs`만 찾아 `*.test.mjs`를 빠뜨린 문제도 발견했다. 이것은 검사 **순서**와 다른, 검사 **발견 범위** 문제다. 두 확장자를 모두 수집하고, ESM 검사가 실패하는 합성 입력을 통해 실행기 실패에 반영되는지 확인했다.

예를 들어 A 실행이 154개, B 실행이 154개 검사를 통과했어도 두 목록이 다르면 같은 범위를 확인한 것이 아니다. 검사 수는 크기만 알려준다. 비교하려면 실행한 소스와 검사 목록도 함께 알아야 한다. 상세 재현은 [backend DATA-48](../../../../godieor-backend/docs/tasks/DATA-48-ott-support-alignment.md)에 남기고, 이 글의 주제는 의존성 설계에 한정한다.

## 다른 상황에 적용한다면

API 서버가 잠깐 내려가도 순수 날짜 변환 검사는 실행할 수 있다. 반대로 migration이 실패한 DB에서 API 검사를 계속하면 정상 상태를 전제로 한 오류만 늘어난다. 다음 검사를 계속할지는 “앞 검사가 실패했는가”보다 “다음 검사에 필요한 입력이 유효한가”로 판단해야 한다.

생각해 볼 질문: 실행 결과가 `성공 / 실패` 두 가지뿐이라면, “필요한 DB가 없어 실행하지 못한 검사”는 어디에 넣어야 할까? 그 선택이 잘못되면 개발자가 어떤 원인을 오해할까?
