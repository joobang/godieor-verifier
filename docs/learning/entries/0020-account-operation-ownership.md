# LEARN-0020 · 늦게 끝난 요청이 최신 화면을 덮지 못하게 하기

설정을 바꾸는 요청 두 개가 시작한 순서대로 끝난다는 보장은 없다. 로그아웃한다고 이미 시작한 요청이 모두 사라지는 것도 아니다. GODIEOR의 계정 상태 코드에서는 이런 순서 차이로 오래된 설정이 화면에 돌아오거나, 이전 작업이 새 작업의 진행 표시를 지우는 결함을 합성 검사에서 재현했다.

이 문제를 이해하려면 “요청이 성공했는가”에 더해 **지금 이 요청이 이 상태를 바꿀 자격이 있는가**를 물어야 한다.

## 같은 계정에서도 응답은 역전될 수 있다

다음은 구조를 이해하기 위한 **가상 시간 순서**다.

| 순서 | 일어난 일 |
|---|---|
| 1 | 설정 A를 저장하는 요청 시작 |
| 2 | 사용자가 다시 바꾼 설정 B를 저장하는 요청 시작 |
| 3 | B 요청 응답이 먼저 도착해 화면에 B 반영 |
| 4 | A 요청 응답이 늦게 도착 |

도착한 응답을 모두 적용하면 마지막 화면은 A가 된다. 두 요청의 계정은 같다. 따라서 “현재 로그인한 계정의 응답인가”만 검사해서는 이 결함을 막을 수 없다.

프로젝트에서는 설정 변경을 시작할 때 증가시키는 번호인 `settingsMutationRevision`을 사용한다. 요청이 시작할 때의 번호와 지금 번호가 다르면, 그 사이 더 새로운 변경이 시작됐다는 뜻이다. 오래된 응답은 현재 설정을 덮지 못한다.

## 계정 경계와 작업 경계는 다른 문제다

| 구분 | 확인하는 질문 | 막는 문제 |
|---|---|---|
| 세션 generation | 이 요청을 시작한 로그인 세션이 지금도 유효한가? | A 계정 응답이 B 계정에 반영 |
| 변경 revision | 요청 이후 더 새로운 설정 변경이 시작됐는가? | 같은 계정의 오래된 저장 응답이 새 설정을 덮음 |
| 작업 UUID | 지금 진행 표시를 소유한 작업이 나인가? | 끝난 옛 작업이 새 작업의 busy 표시를 지움 |

하나의 “최신 요청 번호”로 모든 것을 처리하면 어떤 상태의 최신성을 검사하는지 불분명해진다. 이 코드에서는 세 경계를 나누어 각각 필요한 곳에서 확인했다.

## `defer`는 정리를 보장하지만 소유권은 보장하지 않는다

Swift의 `defer`는 함수 범위를 나갈 때 정리 코드를 실행하는 데 사용한다. 하지만 다음 같은 정리는 비동기 작업이 겹칠 때 문제가 된다. 아래는 **설명용 의사코드**이며 실제 소스를 그대로 옮긴 것이 아니다.

```text
옛 작업 시작 → busy = true
로그아웃 → 새 계정 로그인 → 새 작업 시작 → busy = true
옛 작업 종료 → defer에서 busy = false
```

마지막 줄은 새 작업이 실행 중인데도 진행 표시를 지운다. 실제 수정에서는 시작한 작업의 UUID를 저장하고, `endBusy`가 현재 소유 UUID와 일치할 때만 해제한다. 정리 코드도 공유 상태를 수정하므로 소유권 확인이 필요하다.

관련 코드는 [Account.swift](../../../../godieor-app/ios/GODIEOR/Account.swift)의 `beginBusy`, `endBusy`, `saveSettings`에서 읽을 수 있다.

## 왜 요청 취소만으로 해결하지 않았나

다음 표는 원본에 기록된 선택을 이해하기 위한 사후 대안 비교다. 모든 대안을 당시 실제 실험했다는 뜻은 아니다.

| 대안 | 도움이 되는 점 | 남는 문제 |
|---|---|---|
| 요청이 끝날 때까지 새 조작 차단 | 겹치는 작업을 줄임 | 느린 요청 동안 로그아웃·새 세션까지 막을 수 있음 |
| 이전 요청 취소 | 불필요한 작업을 줄임 | 이미 서버에 반영된 쓰기를 되돌리는 장치는 아님 |
| 상태 적용 시 세션·revision·소유권 확인 | 늦게 끝난 요청의 화면·진행 상태 변경을 제어 | 각 상태의 유효 조건을 관리해야 함 |

선택한 수정은 세 번째 방식을 중심으로 한다. 새 세션을 발급하면 이전 설정·찜 snapshot과 진행 상태를 먼저 비워, 새 계정의 첫 조회가 실패해도 이전 계정의 값이 남지 않게 했다.

이것이 여러 기기의 서버 쓰기 순서까지 해결한다는 뜻은 아니다. 여기서 설명하는 revision은 앱 안에서 오래된 응답의 적용을 막는 장치다. 서버의 저장 충돌과 버전 처리는 별도 계약으로 확인해야 한다.

## 실제로 재현한 것

실제 `AccountState`에 가상 HTTP 응답·메모리 세션 저장소를 연결해 검사했다. 코드의 복사본을 따로 만든 검사가 아니다. 수정 전 15개 중 4개가 실패했고, 수정 후 15개가 통과했다. 네 결함은 이전 계정 값 잔류, 로그아웃 뒤 busy 잔류, 이전 `defer`의 새 작업 간섭, 늦은 설정 응답 덮어쓰기였다.

이 결과는 개발 중 합성 재현이다. 당시 unsigned iOS 빌드도 성공했지만, 그 검사만으로 실제 Google 로그인·Keychain·두 기기 왕복까지 확인한 것은 아니다. 재현 명령과 당시 고정 코드 SHA는 [APP-AUTH-13](../../../../godieor-app/docs/ai/tasks/APP-AUTH-13.md)에 있다. 이번 편집에서 해당 검사를 재실행하지 않았다.

생각해 볼 질문: 계정이 같고 revision도 같지만 busy UUID가 다른 경우가 가능한가? 그때 옛 요청의 정리 코드는 무엇을 해도 되고 무엇을 하면 안 될까?
