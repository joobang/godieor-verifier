# LEARN-0008 · 공지 발견과 일정 확정을 분리하는 날짜 게이트

종류: 사용자 날짜 정책을 구현한 로컬 후보 처리 사례. 제품 운영 사고/전수 자동화 성과가 아니다.
상태: 작성자 빌드/자체 검사/공개 RSS 실행 확인, 제품 publish·독립 검증 전. 2026-11-09 KST.

원본: backend [ADR-010](../../../../godieor-backend/docs/decisions/010-ott-candidate-staging.md),
[사용법](../../../../godieor-backend/docs/ott-candidates.md), [작업 기록](../../../../godieor-backend/docs/tasks/DATA-02-ott-candidates.md).

자료에 날짜 문자열이 있다는 사실만으로 OTT 최초 공개일을 확정할 수 없다.
후보 발견에서는 발행일/출처/변경 fingerprint만 기록하고, 검토에서 플랫폼·시장·드라마·최초 공개 근거·정확한 날짜를 받는다.
연/월만 있으면 후보 보류, 시각·시즌은 null 허용이다. 재수집 중복과 공지 변경 후 이전 검토 재사용을 각각 검사한다.

실제 결과: RSS 공지 77개 수집, 공식 링크의 작성자 검토 후 4개 후보 내보내기(총 공지 후보 80개).
제품 API/DB 반영은 0건이다. TypeScript 빌드 성공과 최초 14개 자체 반례 검사 통과를 독립 검증/정확도 측정으로 확대하지 않는다.
처음 빌드에서 중복 id 필드 오류가 발생해 제거 후 성공했다. 제품 장애가 아닌 개발 중 형식 오류다.

설명할 선택: 새 DB 서버 없이 파일 staging으로 검토 흐름부터 확인하고, publish용 안정 작품/시즌 키와 권한은 다음 단계로 남겼다.
공지 단위/작품 단위가 다르므로 단순 URL 하나를 모든 이벤트의 영구 식별자로 사용하면 안 된다.
질문: 공지가 수정되면 왜 재검토하는가? RSS 본문이 바뀌지 않으면 어떤 한계가 있는가? 날짜가 없는 작품은 언제 다시 확인해야 하는가?
사용자의 이해도·검토 완료·커버리지 성과는 미기록이다. 코드·입력 정책·출처가 바뀌면 이 기록을 재검토한다.


후속 코드 리뷰에서 내보내기 파일 잔존과 A→B→A 옛 검토 재사용이 재현됐다.
발생 token·파일 무효화로 수정하고 작성자 15개 회귀 검사 통과를 확인했다.
리뷰 범위/재확인 기록은 [코드 리뷰](../../../reviews/2026-11-09-ott-candidates.md)에 연결한다.
제품의 독립 통합 검증 결과로 확대하지 않는다.

재확인에서 v1 상태를 승계할 경로가 없다는 추가 지적도 받았다.
v1 후보/이력 보존 변환과 손상 상태의 export 보존을 구현하고 작성자 최종 17개 검사 통과를 확인했다.

BE-03 후속: 후보 core/IO/CLI를 ott-candidates 기능 모듈과 Service/Repository/Client로 옮겼다.
기존 17개 규칙 검사를 유지하고 DB-free DI/CLI 검사를 추가했다. 최신 구조·검사 범위는 LEARN-0009/BE-03 원본을 따른다.
기존 코드 리뷰는 당시 고정 SHA의 이력이며 새 구조 전체를 승인한 기록이 아니다.
