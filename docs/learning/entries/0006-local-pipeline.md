# LEARN-0006 · 외부 API보다 가상 제공처를 먼저 연결한 이유

일정을 보여 주려면 외부 API에서 가져온 값을 DB에 넣고 앱으로 보내면 될 것처럼 보인다. 하지만 제공처 응답에는 작품·날짜·지역·플랫폼이 서로 다른 방식으로 들어 있다. 네트워크가 정상이어도 날짜를 잘못 해석하거나 같은 일정을 두 번 저장할 수 있다.

GODIEOR는 초기에 **가상 제공처 7건으로 저장·조회까지 연결하는 경로**를 먼저 만들었다. 실제 일정을 확보하기 전에, 원천에서 온 정보를 어떤 의미로 저장하고 다시 수집해도 같은 일정을 유지할지 확인하려는 선택이었다.

## 파이프라인은 단계별 약속이다

여기서 파이프라인은 다음과 같이 입력을 제품 데이터로 바꾸는 경로를 말한다.

```text
제공처 응답
  → adapter: 제공처 형식을 읽는다
  → normalize: 제품의 작품·이벤트·날짜 표현으로 바꾼다
  → identity 매핑: 기존 이벤트인지 찾는다
  → publish: 한 범위의 변경을 DB에 반영한다
  → API: 앱이 조회할 형태로 돌려준다
```

이름을 붙이는 것만으로 책임이 나뉘지는 않는다. 예를 들어 adapter가 네트워크 재시도를 하는 동안 DB의 공개 데이터가 반쯤 바뀌어 있으면, 단계가 파일별로 나뉘어 있어도 사용자에게 불완전한 결과가 보일 수 있다.

그래서 외부 수집 I/O와 DB publish 트랜잭션을 나누었다. 필요한 입력을 수집·검증한 뒤, 게시하는 범위의 DB 변경을 하나의 트랜잭션으로 묶는다. 트랜잭션은 그 범위에서 일부만 반영되는 일을 막는 장치다. 모든 제공처가 한 번에 성공한다는 보장은 아니다.

## 날짜가 바뀌어도 같은 일정이어야 한다

가상 작품 X의 출시일이 11월 17일에서 24일로 바뀌었다고 하자. 이벤트 키를 `제목+날짜`로 만들면 새 이벤트가 생기고 이전 이벤트가 남을 수 있다. 반대로 출처의 안정적인 이벤트 ID를 매핑하면 기존 이벤트의 날짜와 변경 이력을 갱신할 수 있다.

같은 작품이라도 한국·일본, 극장·OTT, 다른 게임 플랫폼의 공개는 별개일 수 있다. 따라서 “같은 제목인가”와 “같은 공개 사건인가”는 다른 질문이다. 이 구분을 가상 입력에서 먼저 표현할 수 있어야 실제 제공처를 붙였을 때도 의미를 지킬 수 있다.

다음 표는 원본에 기록된 선택을 이해하기 위한 사후 대안 비교다. 모든 대안을 당시 실제 실험했다는 뜻은 아니다.

| 시작 방법 | 장점 | 먼저 떠안을 위험 |
|---|---|---|
| 실제 API부터 연결 | 실제 응답 구조와 접근 조건을 빨리 확인 | 인증·네트워크·변환·저장 오류가 한꺼번에 섞임 |
| 단위 함수만 구현 | 날짜 변환 등을 작게 확인 | DB 제약·ID 매핑·조회 연결 문제는 남음 |
| 가상 입력으로 저장·조회까지 연결 후 실제 API 확장 | 실패 입력을 통제하며 경계 연결을 확인 | 실제 API의 누락·변경·이용 조건은 별도로 조사해야 함 |

초기 구현은 세 번째 방식을 택했다. 실제 API를 나중까지 미루어도 된다는 일반 원칙은 아니다. 원천이 필요한 날짜를 제공하는지 조사하는 일은 병행해야 한다. 가상 입력의 성공은 실제 데이터 확보율을 말해 주지 않는다.

## JSON 문자열이 다르다고 데이터가 달라진 것은 아니다

다음 두 객체는 설명용 예제다.

```json
{"date":"2026-11-17","region":"KR"}
{"region":"KR","date":"2026-11-17"}
```

객체 키 순서만 다르다. PostgreSQL의 `jsonb`는 객체 키 순서를 보존하지 않는다. 따라서 읽어 온 객체와 입력 객체를 단순 문자열로 비교하면 의미가 같은데도 변경으로 볼 수 있다. 이 프로젝트는 canonical 비교에서 키 정렬을 사용하도록 예방 설계했다. 배열의 순서까지 무조건 정렬해도 된다는 뜻은 아니다. 배열 순서에 의미가 있다면 보존해야 한다.

이것은 초기 문서에서 예방 조치로 기록한 항목이며, 당시 실제 운영 장애를 해결했다고 쓰면 안 된다. DB 동작 근거는 [PostgreSQL 16 JSON 문서](https://www.postgresql.org/docs/16/datatype-json.html)에 있다.

## 실제 수집을 붙이자 새 문제가 생겼다

이후에는 일일 수집이 과거 누락을 채우지 못하는 문제가 드러났다. 매일 최근 구간만 확인하면 제품이 약속한 2026년 초의 일정은 영원히 조회하지 않을 수 있다. 그래서 과거 범위를 채우는 **backfill**과 최근 변경을 확인하는 **daily**를 구분했다. 실제 수집 시작점과 범위는 [ADR-023](../../../../godieor-backend/docs/decisions/023-2026-backfill-and-missing-date.md)이 설명한다.

목록에서 사라진 영화도 단순히 삭제하지 않았다. 목록 부재는 필터·페이지·원천 변경 때문일 수 있기 때문이다. 당시 영화 뮤티니는 같은 공식 ID의 상세에서 날짜가 빈 값인 것을 확인한 뒤, 기존 ID와 이전 날짜 이력을 유지하며 날짜를 미정으로 바꿨다. 반면 IGDB의 빈 응답은 원인이 확정되지 않아 자동 삭제 근거로 쓰지 않았다.

이 두 사례는 초기 파이프라인의 목적을 보여 준다. 네트워크 응답을 저장하는 데서 끝나는 것이 아니라, 입력이 말해 주는 범위 안에서 같은 사건의 변경을 반영해야 한다.
