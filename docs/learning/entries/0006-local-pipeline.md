# LEARN-0006 · 파이프라인을 가상 제공처부터 연결한 이유

종류: 초기 구현/예방 설계. 운영 장애 해결·성능 성과가 아니다. 사용자 이해/독립 검증 완료도 아니다.
근거: backend ADR-009, docs/reviews/2026-11-09-contract-review.md, docs/tasks/BE-01-local-pipeline.md.
고정 backend/계약/migration 참조는 docs/contracts/reference.json.

외부 API를 연결하기 전에 어댑터→정규화→안정 ID 매핑→원자적 publish→조회 경계를 구성했다.
가상 7건으로 네 분야/시즌/기기/미정의 표현과 로컬 API 구동까지 연결했다. 이는 실제 데이터 확보율 검증이 아니다.
공식 출처 조사에서 OTT의 플랫폼 가용성과 한국 시즌 최초 공개일이 서로 다른 정보임을 확인해, 근거 없는 날짜 생성 대신 보강 출처가 필요하다고 기록했다.

DB JSONB는 객체 키 순서를 보존하지 않아 단순 JSON.stringify 비교가 변경 이력을 과도하게 만들 수 있다.
canonical 비교 시 키를 정렬하는 예방 조치를 넣었다. 실제 장애 재현이나 반복 수집 테스트는 아직 하지 않았다.
팀도 이름보다 제공처 팀 ID를 매핑하고, 수집 실패는 마지막 성공 시각을 덮어쓰지 않게 구성했다.

실제 수행: 지원 런타임 버전 확인, 전용 DB 생성/초기 migration, Prisma introspection/generate, TypeScript build,
가상 수집 CLI, Nest 시작, 공개 API 응답 조회. 테스트 suite/독립 DB/권한 격리는 미실행.
스스로 설명할 질문: 왜 외부 수집 I/O를 DB publish 트랜잭션 밖에 두나? 무엇을 원자적으로 공개해야 하나? 플랫폼 목록이 공개일 근거가 아닌 이유는?

## DATA-73 · 실제2026 백필과 날짜 철회 재확인

게임/EPL의 일일 수집만으로2026년 과거 누락이 채워지지 않음을 실제 DB에서 확인했다. backfill 시작점을 게임2026-01-01/영화2026년/EPL2025시작 시즌으로 고정하고, 제공처·mode·force 실행을 분리했다. 현재 실제 게임4870→29914(새25044), EPL380→760(이전 시즌380추가), 영화1902→1909(새7) 적재. EPL 이전 시즌의2025년186경기 저장과2026년 이후 제품 조회를 구분한다. 초기 가상7건과 달리 이번은 실제 입력·제품 DB 결과이며 여전히 전체 제공처 전수 정확성/독립 승인은 아니다.

뮤티니의 공식 상세 openDt 빈 값을 확인해, 목록에서 사라진 기존 영화를 동일 ID로 재조회한 뒤 date_only→unknown으로 바꾸는 일반 경로를 추가했다. 제작연도/UTC시각/취소 상태를 추정하지 않았다. event ID·이전 날짜 이력/previousTime을 보존하고 달력에서 빼 미정 목록에 표시했다. 반복 실제 영화 수집 후 전체32683 event 행·이력(가상7 포함)이 불변이었다. IGDB 기존49 ID의200/빈 배열은 명시 날짜 철회와 달라 삭제·취소로 추정하지 않았고 원인을 검토 대기로 남겼다.

실제 게임35표본·EPL새380 공식 대조, KR/WORLD 게임+EPL 월별 API30115 ID와DB 일치, 기존7252ID 보존/7207행·이력 불변/45갱신, 최종 자체310개 및 고정digest 일회용DB 회귀가 근거다. daily 재실행은 새 게임/EPL0이었으나 메타데이터 갱신2도 있어 전부 불변이라고 하지 않는다. 일일 자동 운영/미정 게임·원천ID 이동·OTT 자동 검토·클라우드는 후속이다. 근거는 backend ADR023/DATA73/원천 범위 표. 스케줄·수집 범위·원천 의미/날짜 갱신·리뷰 정책이 바뀌면 설명과 측정 범위를 재검토한다. 사용자 이해도·성과 미측정.
