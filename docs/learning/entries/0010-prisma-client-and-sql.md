# LEARN-0010 · Prisma를 쓰면서 SQL을 남긴 이유

GODIEOR backend는 Prisma를 쓰고 있었지만 단순 조회까지 raw SQL로 작성돼 있었다. 사용자는 “Prisma인데 왜 raw SQL 위주인가”라고 지적했고, Client를 기본으로 사용하도록 요청했다. 수정의 핵심은 조회를 전부 한 방식으로 통일하는 것이 아니라, **생성 타입으로 표현할 수 있는 조회와 직접 계산해야 하는 조회의 경계**를 정하는 것이었다.

## ORM을 도입해서 얻으려던 것은 무엇인가

Prisma Client는 DB 모델로부터 조회 API와 타입을 생성한다. 필터·관계 조회 같은 일상적인 쿼리를 그 API로 표현하면 코드와 스키마의 연결이 드러난다. 필드가 바뀌었을 때 영향받는 코드를 타입 검사로 찾는 데도 도움이 된다.

다음은 이 프로젝트의 실코드를 인용한 것이 아닌 **설명용 예제**다.

```ts
// 모델에서 생성된 필드로 조회한다.
prisma.event.findMany({ where: { status: "scheduled" } });

// 결과 타입을 직접 적어 준 raw SQL이다.
prisma.$queryRaw<{ id: string }[]>`SELECT id FROM event`;
```

둘째 줄의 `<{ id: string }[]>`만으로 SQL이 정말 문자열 id를 반환한다고 증명되지는 않는다. 개발자가 반환값의 타입을 지정한 것이다. SQL을 바꾸면서 타입 선언을 그대로 두면 둘이 어긋날 수 있다. Prisma 공식 문서도 [raw 결과 타입을 직접 지정할 때의 주의점](https://www.prisma.io/docs/orm/v7/prisma-client/using-raw-sql/raw-queries#typing-queryraw-results)을 설명한다.

## 이 앱의 달력 조회에는 계산이 필요했다

달력은 날짜만 있는 일정과 실제 시각이 있는 일정을 한 목록에 보여 준다. 날짜만 있는 일정은 원래 날짜를 지켜야 하고, 실제 시각은 사용자가 고른 시간대의 날짜로 바꿔 정렬해야 한다.

가상 예로 `2026-11-17`이라는 한국 공개일은 그 날짜 그대로다. 반면 `2026-11-17T20:00:00Z`라는 가상 시각은 KST에서 11월 18일이다. 두 값을 같은 기준으로 정렬하려면 “표시용 날짜”를 계산해야 한다.

이 프로젝트의 조회는 계산된 날짜를 이용한 정렬·페이지 경계, 날짜별 전체 개수와 상위 두 행을 구하는 window 집계를 사용했다. 당시 Client의 일반 `orderBy`로 필요한 계산식을 표현할 수 없어 이 부분을 SQL 예외로 남겼다. “SQL이 더 빠를 것”이라는 추측을 선택 근거로 쓰지는 않았다.

다음 표는 원본에 기록된 선택을 이해하기 위한 사후 대안 비교다. 모든 대안을 당시 실제 실험했다는 뜻은 아니다.

| 방법 | 장점 | 이 프로젝트에서 감수할 비용 |
|---|---|---|
| 모두 raw SQL | 필요한 DB 연산을 직접 표현 | 단순 조회도 수동 타입·SQL 유지 비용을 부담 |
| 모두 Client | 모델·조회 타입의 연결이 일관됨 | 복합 날짜 정렬·집계의 의미를 그대로 표현하기 어려움 |
| Client 기본 + 좁은 SQL 예외 | 일상 조회의 타입 이점과 DB 계산을 함께 사용 | 예외 위치·이유·입출력 검사를 별도 관리 |

사용자 요청에 따라 세 번째 방식을 적용했다. 미정 목록·이전 날짜 이력·연결 확인은 Client로 바꾸고, 날짜 계산 조회와 DB 잠금처럼 이유가 있는 부분은 예외 목록에 남겼다.

## SQL 예외에는 서로 다른 두 종류의 검사가 필요하다

입력은 `Prisma.sql` 등의 바인딩을 사용한다. 사용자 값을 SQL 문자열에 이어 붙이지 않기 위해서다. 출력은 `unknown`으로 받은 뒤 Zod로 행 모양과 값의 타입을 확인한다. 바인딩은 입력을 안전하게 전달하는 문제이고, 출력 검사는 DB에서 돌아온 값이 코드의 기대와 맞는지 확인하는 문제다.

그렇다고 출력 스키마가 날짜 정렬의 의미까지 증명하지는 않는다. 모든 행이 올바른 타입이어도 날짜를 잘못 계산할 수 있다. 그래서 기존 API 응답과 양방향 페이지 이동 결과를 비교하는 검사를 함께 남겼다. 구체적인 예외와 회귀 범위는 [쿼리 정책](../../../../godieor-backend/docs/query-policy.md)이 소유한다. 고정 형태 SQL을 늘릴 때에는 생성 타입을 제공하는 TypedSQL도 검토하도록 정했다.

## 단순 조회로 바꾸어도 도메인 판단은 남는다

이전 공개일을 찾을 때 가장 최근 이력 한 행만 읽으면 안 된다. 그 행은 제목만 바뀐 기록일 수 있기 때문이다. 구현은 이력을 100행씩 읽어 실제 시간 값이 달라진 기록을 찾도록 했다. 당시 임시 DB에서는 제목 변경 이력 105개 뒤에 있는 이전 날짜를 찾는 경우를 확인했다.

이 방식의 비용은 읽어야 하는 이력 수에 따라 늘어난다. Client로 바꾸었다는 사실만으로 성능이 개선됐다고 말할 수는 없다. 이력이 커지면 스캔 비용을 측정하고, 시간 변경을 별도 저장하는 구조나 다른 쿼리를 다시 비교해야 한다.
