# LEARN-0010 · Prisma의 타입 보장과 필요한 SQL을 구분하기

2026-11-09, 실제 개발 선택과 예방 설계·작성자 실행 기록. 운영 장애/성과 수치·사용자 이해도는 기록하지 않는다.

사용자는 Prisma인데 raw SQL 위주인 이유를 물었고 앞으로 Client 우선으로 작성하도록 요청했다. 단순 미정 목록·이전 날짜 이력·연결 확인을 Client로 바꾸고, 요청 시간대 계산 정렬과 일별 window 집계만 SQL로 남겼다. 상세 예외는 backend/docs/query-policy.md / ADR-012, 작업은 BE-04다.

Prisma Client는 스키마로 생성한 where/orderBy/관계 타입을 제공한다. `$queryRaw<T>`의 T는 개발자가 쓴 주장이고 SQL 의미/반환 shape를 증명하지 않는다. 현재 동적 쿼리는 바인딩 SQL로 실행하고 unknown 결과를 Zod로 검사한다. TypedSQL은 고정 형태 SQL 도입 시 우선 검토한다.

이력에서 제목만 바뀐 행은 시간 변경이 아니다. JSON object 키 순서도 의미를 바꾸지 않는다. Client JSON-path 필터 후100행씩 keyset 조회해 실제 시간 변경을 찾았다. 105개의 제목 변경 이력 뒤 실제 이전 날짜를 찾는 임시DB 검사를 통과했다. 성능 측정/개선 수치는 없으며 조회 비용은 이력 수에 의존한다.

실행: 6aac1d3 기준 자체33개, 이전 빌드21API/양방향 커서 동일. 별도 컨텍스트 Lovelace는 추가 지적 없음을 보고했으며 실제DB 검사는 하지 않았다. 작성자DB 실행과 구분한다. 질문: 언제 Client보다 SQL이 더 정확한가? 수동 제네릭과 runtime 검사는 각각 무엇을 보장하는가?

관련 코드/정책/제공처 문서가 바뀌면 원본과 이 주장을 다시 검토한다.
