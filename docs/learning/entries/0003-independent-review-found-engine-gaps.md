# 24개 검사가 통과했는데 독립 리뷰는 왜 결함을 찾았나

실제 **개발 중 결함** 사례다. 사용자에게 배포된 서비스 장애는 아니다.
초기 판정 엔진의 24개 자기 검사는 통과했지만, 구현 대화를 상속하지 않은 리뷰가 4건을 재현했다.

## 발견과 수정

| 관찰 | 원인 | 선택한 수정 | 확인 근거 |
|---|---|---|---|
| 새 앱 SHA·새 리뷰에 이전 검사 결과를 붙일 수 있음 | 전체 report binding만 있고 개별 검사 binding이 없음 | 검사별 run ID·head SHA·기준 hash를 확인 | 이전 check 재사용이 ERROR가 되는 재현 검사 |
| 스키마가 거부하는 배열 settings 등이 집계기를 통과 | 스키마와 수동 validation이 서로 다른 계약 적용 | 필수/추가 필드·값 타입 검사를 일치시킴 | 잘못된 입력의 ERROR 회귀 검사 |
| 중첩/Unicode 입력에서 report 없이 크래시 | JSON 처리와 UTF-8 출력 실패 경로 누락 | 입력 오류 처리와 report 임시 파일 후 교체 | CLI exit 3과 JSON/Markdown 생성 확인 |
| 앞 검사 오류 때문에 뒤의 FAIL 이유가 사라짐 | 전체 검사 루프 바깥에서 예외 처리 | 검사별로 오류·실패를 수집 | 배열 순서 양쪽에서 failures 보존 |

수정 후 33개 자기 검사가 통과했고 같은 독립 reviewer가 기존 4개 재현을 다시 확인했다.
근거 원본은 검증 저장소의 `reviews/bootstrap-2026-11-06.md`, 코드 digest manifest,
`tests/test_engine.py`다. 당시 코드는 미커밋 상태였으며 고정 SHA 검증이었다고 표현하지 않는다.

## 무엇을 배울 수 있나

구현자가 생각한 실패만 검사하면 그 전제 밖의 결함은 남을 수 있다.
기존 검사는 ‘리뷰 SHA가 다르면 오류’를 확인했지만 ‘리뷰만 새것이고 실행 결과는 이전 것’인
조합을 확인하지 않았다. 리뷰가 만든 반례를 자동 회귀 검사로 보존하는 것이 이번 개선이었다.

독립 컨텍스트가 모든 문제를 찾는다는 뜻도 아니다. 같은 모델일 수 있고, 실제 OS 환경도
분리되지 않았다. 다음 단계는 고정 snapshot·실제 runner·증거 진위·권한 경계를 구현하는 것이다.

## 대안과 재검토 조건

- schema validation 라이브러리를 쓰면 계약 구현 중복을 줄일 수 있으나 초기 외부 의존성이 생긴다.
- 현재는 작은 고정 계약을 수동으로 검사하며 회귀 검사로 보완한다.
- 계약이 커지거나 같은 불일치가 반복되면 라이브러리 도입/단일 스키마 검증을 다시 검토한다.

## 면접·블로그로 정리할 핵심

‘AI 에이전트를 여러 개 썼다’보다 ‘어떤 전제가 빠져 있었고, 다른 문맥의 검토가 낸 반례를
어떻게 재현 가능한 검사로 바꿨는가’를 설명할 수 있는 사례다.
직접 판단한 부분과 AI가 구현·발견한 부분을 구분해서 설명한다.

스스로 답할 질문:

- 테스트 수가 늘었다는 사실보다 어떤 반례가 추가됐는지가 왜 중요한가?
- SHA binding이 있어도 evidence를 손으로 위조하면 무엇이 남는가?
- 단위 검사와 실제 runner·권한 경계 검사는 각각 무엇을 증명하는가?
