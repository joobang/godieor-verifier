# LEARN-0022 · 실패 원인을 남기면서 비밀은 숨기는 방법

수집 작업이 빨갛게 끝났지만 로그에는 `COLLECTION_FAILED`만 있다면 다시 실행해도 무엇을 바꿔야 할지 알기 어렵다. 반대로 예외 원문을 그대로 출력하면 DB 접속 비밀번호나 API 키가 포함된 URL이 공개 로그에 남을 수 있다. 실패를 설명하려면 예외 문자열을 더 많이 출력하는 대신, 운영자가 다음 행동을 고를 수 있는 구조로 바꾸어야 한다.

## 원문 대신 실패의 위치와 종류를 기록한다

다음은 설명을 위한 가상 예다. DB 예외의 원문에 `postgresql://name:password@host/db`와 실행 SQL이 있고, 프로그램이 제공하는 코드가 `P2028`이라고 하자. 접속 문자열과 SQL은 버리고 아래처럼 기록할 수 있다.

```json
{"provider":"igdb","market":"KR","phase":"publish","errorCode":"DB_TRANSACTION_FAILED","causeCode":"P2028"}
```

`phase`는 수집·정규화·검사·게시 중 어디까지 진행했는지를 뜻한다. 같은 작업에서도 `phase=fetch`, `PROVIDER_HTTP_429`라면 원천의 요청 제한을 확인해야 한다. DB 게시 오류에 적용할 시간 설정을 바꾸어도 HTTP 요청 제한은 해결되지 않는다. `P2028`도 트랜잭션 오류의 분류이며, 그 자체로 네트워크 지연이나 정확한 timeout 원인을 모두 입증하지는 않는다.

구현은 허용한 오류 이름, HTTP 숫자 상태, Prisma 코드, 고정된 네트워크 코드만 남긴다. 처음 보는 오류는 `COLLECTION_FAILED`로 유지한다. 원문의 비밀번호만 정규식으로 지우는 방식도 가능하지만, URL 인코딩·헤더·서버가 되돌려준 요청 본문까지 전부 예측해야 한다. 공개 CI 로그에서는 허용 목록 방식이 더 좁고 검사하기 쉽다. 그 비용은 새로운 오류 분류를 만날 때 목록과 테스트를 보완해야 한다는 것이다.

## 자식 프로세스의 실패도 읽을 수 있어야 한다

OTT 상위 프로그램이 자식 게시 명령을 실행했다고 하자. 자식은 stdout에 `results` JSON을 쓰고 exit1로 종료한다. stderr에는 `.env not found. Continuing without it.`만 남을 수 있다. 환경 변수로 설정을 주는 CI에서는 이 문장 자체는 오류가 아니다. 상위 프로그램이 stderr만 읽으면 실제 게시 오류는 사라지고 이 안내 문장만 실패 원인처럼 보인다.

수정한 경계는 stdout의 JSON에서 실패 코드와 시장·단계만 골라 읽고, 실제 스크립트 이름과 exit code를 함께 보존한다. 게시 CLI가 여러 줄로 JSON을 출력할 수 있으므로 한 줄씩 파싱하는 것만으로는 충분하지 않다. 전체 JSON과 개별 로그 행을 모두 검사한다. 필수 게시 단계가 실패해도 그 전에 끝난 수집 단계의 보고서를 JSON으로 남긴다. 게시 후 감사만 실패했다면 `published=true`를 보존해야 한다. 전체 작업 실패와 이미 커밋된 데이터의 rollback은 같은 뜻이 아니다.

## 실패를 일찍 찾는 검사에도 범위가 있다

설정 검사를 하나로 묶어 TMDB 토큰 누락 시 전체 작업을 중단하면, 정상 키를 가진 영화·게임·EPL 수집도 실행되지 않는다. 공유 DB·서명 설정은 전체 실행의 조건으로 검사하고, 제공처 키는 해당 제공처에만 적용한다. TMDB 키가 없다고 OTT 전체를 조기 종료해서도 안 된다. 기존에 검토한 매핑의 DB 게시와 독립적인 공식 원천 수집은 계속하고, TMDB 발견 누락을 별도로 남긴다. 이 경계는 개발 중 별도 코드 리뷰에서 지적되어 수정했다. 새 HTTP429 오류 이름을 생산하는 코드뿐 아니라 그것을 소비하는 일일 runner의 검증 규칙도 함께 바꾸어야 기존의 일부 성공 결과를 잃지 않는다.

## 시간 제한을 늘리는 것과 빠르게 만드는 것은 다르다

원격 DB에 순차 쿼리를 보내면 전체 시간은 쿼리 수와 왕복 지연의 영향을 받는다. 설명을 위한 가정으로 쿼리 2,000회에 왕복 지연이 각 20ms라면 왕복 비용만 약 40초다. 이는 실제 측정값이 아니다. 로컬에서 통과하던 30초 트랜잭션 제한이 원격에서는 부족할 수 있다는 원리만 보여 준다.

이번 변경은 CI의 범위별 게시 한도를 15분으로 설정할 수 있게 했다. 한 범위의 이벤트와 성공 기록을 함께 commit하거나 rollback하는 기존 경계를 유지하려는 선택이다. 레코드별 commit은 긴 트랜잭션을 줄이지만 일부 게시 뒤 실패하는 새 복구 정책이 필요하다. SQL 일괄 처리와 불필요한 쿼리 제거는 더 근본적인 대안이지만 안정 ID·이력·관계 보존을 별도로 검증해야 한다. 따라서 시간 설정은 우선 실행 한도를 조정하는 것이며, 성능 향상이나 실제 장애 원인 확정으로 표현하지 않는다. 긴 트랜잭션은 잠금 보유·실패 시 재작업 비용이 늘어나므로 운영 소요 시간과 오류를 보고 다시 판단해야 한다.

## 이번 근거의 범위

2026-11-17 실제 Actions 실행 44056014741에는 TMDB 토큰 공백, 제공처 일부 실패, OTT 자식 exit1이 있었다. 기존 코드가 상세 오류를 버렸으므로 당시 오류가 timeout이었다고 확정하지 않는다. 수정 검사는 합성 HTTP/DB 오류, 실제 실패 자식 프로세스, 일부 성공 scope 보존을 대상으로 한다. 실제 Secret 등록과 원격 DB 재실행은 별도 확인이 필요하다. 테스트 통과는 운영 복구나 독립 제품 승인과 구분한다.
