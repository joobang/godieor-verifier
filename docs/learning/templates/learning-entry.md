# LEARN-XXXX · 독자가 이해할 기술 질문 하나

> 작성 지침: 이 파일은 빈 양식이다. 글을 쓸 때 이 안내는 지운다. 작업 결과를 압축해 붙이지 말고, 이 프로젝트를 처음 읽는 개발자에게 선택 과정을 설명한다. 작성 기준은 `docs/system/learning-policy.md`를 따른다.

첫 문단에서 사용자에게 보인 문제 또는 개발 중 풀어야 했던 문제를 구체적으로 설명한다. 실제 장애·개발 중 재현·예방 설계 중 무엇인지 밝힌다. 무엇을 이해할 수 있는 글인지 한 문장으로 이어 쓴다. 작업 ID·해시·검사 수로 시작하지 않는다.

## 무엇이 왜 문제였나

기대 동작과 관찰 동작을 설명한다. 낯선 용어는 처음 나올 때 풀어 쓴다. 코드의 구조나 데이터 흐름이 원인과 어떻게 연결되는지 보여 준다.

## 작은 예제로 원리 이해하기

최소 입력·출력, 요청 순서, 짧은 코드 중 적절한 것을 쓴다. 예제는 실제 재현/실코드 인용/설명용 가상 예제/의사코드 중 하나로 명시한다. 가상의 실행 결과를 실제 결과로 쓰지 않는다.

## 어떤 선택지가 있었나

| 대안 | 얻는 것 | 잃는 것·제약 | 이 프로젝트에 맞는 정도 |
|---|---|---|---|
| 실제 검토한 대안 | | | |
| 선택한 방법 | | | |

당시 선택 이유를 원본 ADR·코드·실험으로 확인한다. 설명을 위해 사후에 추가한 비교는 사후 비교라고 밝힌다. 당시 논의가 없었다면 있었다고 만들지 않는다. 기술의 장점을 나열하는 데서 끝내지 말고 이 문제의 제약과 연결한다.

## 어떻게 적용했고 무엇을 확인했나

수정이 문제를 막는 원리를 설명한다. 실제 확인한 반례와 결과를 문장으로 연결한다. 명령 전체·로그·모든 테스트 수는 원본 작업 카드에 둔다. 원본을 읽지 않아도 본문의 논리를 이해할 수 있어야 한다.

## 비용과 다시 선택할 조건

복잡성·유지보수·관측 범위의 구체적인 한계를 적는다. 규모·계약·플랫폼이 어떻게 바뀌면 선택을 다시 비교할지 설명한다. 측정하지 않은 성능·비용 효과를 만들지 않는다.

생각해 볼 질문은 이 글의 예제를 바꾸어 답할 수 있게 쓴다. 사용자가 이미 이해했다거나 직접 수행한 경험이라고 대신 기록하지 않는다.

## 근거·시점·갱신

- 작성/개정일, 사례 당시 시점, 원본 ADR·작업 카드·코드/검사 기록 링크.
- 재실행한 검사와 과거 기록을 구분한다. 공식 문서의 버전·확인일을 남긴다.
- 새 사례는 주장이 달라질 때 해당 절을 다시 편집하거나 별도 글로 분리한다. 날짜별 작업 요약을 본문 끝에 계속 붙이지 않는다.
- 독립 검증 상태는 해당 원본 링크로 연결한다. 글 작성 여부를 검증 승인이나 이해도와 같은 상태로 취급하지 않는다.
