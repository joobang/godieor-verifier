# 어떤 문제를 풀었나

실제 장애, 개발 중 실패, 예방적 설계 사례 중 무엇인지 먼저 명시한다.
증상·환경·기대 동작·관찰 동작을 구체적으로 쓴다.

## 가설과 실험

| 구분 | 주장/가설 | 확인 방법 | 실제 관찰·근거 | 남은 불확실성 |
|---|---|---|---|---|
| 가설/확정 사실 | | 명령·재현 절차 | 로그/파일:줄/SHA/출처 | |

## 왜 이 방법을 골랐나

대안, 제약, 장단점, 선택 이유, 포기한 이점, 선택을 다시 바꿀 조건을 적는다.
사용자 승인과 AI 제안을 구분한다. ADR이 있으면 원본 링크를 건다.

## 결과와 한계

실제 검사 결과·비교·run ID를 남긴다. 실행하지 않은 실험과 추정 수치는 쓰지 않는다.
결론을 반박할 수 있는 경우와 후속 검증을 적는다.

## 핵심 기술을 내 말로

원리를 작은 예제로 풀고 개념을 적용하면 안 되는 경우도 설명한다.

## 스스로 답할 질문

- 왜 더 간단한 방법을 선택하지 않았나?
- 데이터/규모/비용 조건이 바뀌면 무엇이 달라지나?
- AI의 결과를 무엇으로 확인했나?

## 면접 설명 초안

상황 → 내 책임과 AI 활용 범위 → 판단 → 실행 근거 → 결과/한계.
본인이 직접 설명·검토하기 전에는 ‘설명 완료’라고 표시하지 않는다.

## 블로그로 발전시킬 때

독자, 핵심 질문, 실제 재현 예제, 공개해도 되는 근거, 추가 실험을 적는다.

## 근거와 갱신 이력

공식 문서 URL·조회일·버전, 코드 SHA·파일, run/report 경로, 변경 이유를 남긴다.
관련 코드/문서가 바뀌면 `needs-recheck`로 표시한다.
